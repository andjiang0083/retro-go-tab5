## 1. P1 清单（建议并入 v0.4.2）

### P1-1 充电使能只补在竖屏驱动，横屏副本仍是旧的 → 横屏构建充电会复发
- 位置：`drivers/display/mipi_dsi_tab5.h`（对照 `mipi_dsi_tab5_p.h:266-273`）
- 证据：`grep -n bsp_set_charge mipi_dsi_tab5*.h` 只命中 `_p.h` 一处；两个文件在 IO 扩展器初始化段相同，但只有一个补了 `bsp_set_charge_qc_en(true)` / `delay(50)` / `bsp_set_charge_en(true)`。
- 影响：`config.h` 的 `RG_SCREEN_DRIVER == 3` 才走竖屏驱动；谁手动切回横屏（编号 2）构建，就会重新得到"插 USB-C 不充电、INA226 分流恒为 0"的老 bug，而且日志里看不出来（和这次踩坑的形态完全一样）。
- 改法（二选一）：① 把这 3 行照抄进 `mipi_dsi_tab5.h`，并在两处互相加"⚠ 此逻辑必须双份同步"注释；② 更好的做法是把"扩展器 init + 充电使能"抽成一个共用函数（如 `tab5_power_init()`）放独立头文件，两个驱动都调它 —— 从根上消灭双份。
- 验证：切 `RG_SCREEN_DRIVER 2` 编译，真机日志出现 `charging enabled: CHG_QC=on, CHG_EN(P7)=high`。

### P1-2 字模推进长度固件与 PC 工具口径不同，靠"全是 8x8"侥幸等价
- 位置：固件 `rg_touch_overlay.c` 的 `load_glyphs()`（`nbytes = ceil(w*h/8)`）vs `tools/preview-touch-overlay.py:73`（`nbytes = h`，每行一字节）
- 证据：实测该字库 **191 个字形全部 8×8**（脚本逐条扫描 `fonts/basic8x8.c` 确认），此时 `ceil(64/8) == 8 == h`，两种算法才等价。
- 影响：一旦字库混入 `width < 8` 的字形（比如自制小图标、窄符号），**固件**会按位紧凑长度推进，而真实数据是每行一字节 → 后续所有字形整体错位，表现为"文字乱码/镜像"——正是 2026-09-29 用户反馈的那类故障。更麻烦的是 PC 工具会保持正确，两边不一致，排查时容易怀疑错地方。
- 改法：把固件 `load_glyphs()` 的推进改成 `nbytes = g->height`（与真实排法、与 PC 工具三者一致），并在函数上加一行注释"仅支持每行一字节的 8x8 字库"；或明确断言 `width == 8 && height == 8`，遇到别的字形直接报错而非静默错位。
- 验证：构造一个 6×8 字形放进字库，重新编译看标签是否仍正确渲染（当前会乱，改后正常）。

### P1-3 PPA 分支与现在的线性映射不兼容，却留着"重开前必读"的邀请
- 位置：`mipi_dsi_tab5_p.h:671-699`（PPA 分支）vs 同文件 `656-664`（线性映射说明）
- 证据：PPA 分支按**老 90° 映射**写：`rotation_angle = ANGLE_270`、`out.block_offset = (x0, y0)`、`byte_swap = true`，而当前实现是 `px = lx, py = ly` 的线性 1:1（不旋转）。开关 `ppa_allowed = false`（同文件 329 行）现在把它关死了，所以线上没问题。
- 影响：文件里那段注释（"重开前必读：① 确认对齐 ② …"）会诱导后人只改 `ppa_allowed = true` 就重开 PPA；那样除了对齐以外全部前提都已失效，结果是画面旋转错位（属于"看着正常但全错"的那类）。
- 改法：在 `ppa_allowed` 那一行旁写死一句"⚠ 本分支仍按 90° 映射编写，与现有线性映射不兼容：重开必须重写为 `ANGLE_0` + `scale_x/y=3` + 落点 `(0,0)`"，或者干脆把这段不可用代码删掉留一句结论注释（PPA 按块调用已被实测判死）。
- 验证：代码走查即可（无运行时验证需求）。

### P1-4 关机路径"等所有键松开"超时无限，触摸残留点会让关机永久卡住
- 位置：`rg_system.c:899` `rg_input_wait_for_key(RG_KEY_ALL, 0, -1)`（超时 −1 = 无限）；`rg_input.c:455-456` 注释自己写着 ST7123 的多点上报"第 0 点可能是上一次的残留坐标"
- 证据：本机唯一输入是触摸屏（`config.h` 里物理按键只有 Reset/Boot）。老平台上"按键松开"由硬件保证会到；触摸屏上残留/幽灵触点是已知现象（同一份代码为此特意遍历了所有触点而不是只看 `px[0]`）。
- 影响：只要关机瞬间有一个残留触点被读到，`RG_KEY_ALL` 永不为 0 → `shutdown_cleanup()` 卡在等待里，表现为"点关机后黑屏等待、不重启也不掉电"。
- 改法：给等待加有限超时（如 3000ms）后直接继续关机；顺带在日志里记一行"键未全松开，超时继续"。
- 验证：真机按住虚拟键不放，从菜单触发关机 → 观察 3s 后是否正常完成关机。

## 2. P2 清单（择机清理，按主题分组）

### 2.1 生产构建里的开发期插桩 / 死用途代码
1. **每秒无条件跑"帧率数字刷新"段**：`mipi_dsi_tab5_p.h:597-612` 在 `tab5_perf_report()` 里擦除物理 `x[640,680) y[584,696)`（40×112）、整屏调一次 `rg_overlay_blit_linear()`、再 `esp_cache_msync` 写回 161,280B。而它服务的帧率数字在 release 里根本没画（`rg_touch_overlay.h:85` `RG_OVERLAY_SHOW_FPS 0` → `blit_fps/draw_fps_text` 不编译）。澄清：这段不产生可见瑕疵（擦除区紧接着被同一次 overlay 重画覆盖，且写回带覆盖了整个擦除区），但每秒一次白工，且擦除区正好横切 R 肩键一角。
   → 改法：整段用 `#if RG_OVERLAY_SHOW_FPS` 包起来。
2. **PPA 探针仍在生产**：同文件 `559` `#if 1` + `tab5_ppa_frame_probe()`，开机第 1 秒申请 76,800B + 691,200B PSRAM（合计 768KB）、跑 5 次 PPA、打 6 行日志。
   → 改法：置 `#if 0`（结论已拿到），或整段删除只留结论注释。
3. **`%llu/%lld` 进了 IDF 日志**：`mipi_dsi_tab5_p.h:637` 的 `RG_LOGI("... (%llums display / %lldms total)")`。ESP-IDF 的 `esp_log` 不支持长度修饰符 —— 同一文件 499 行还专门写着"只用整数格式化"。
   → 影响：这行数字必打错（本次是行末参数，不会连带错位其它参数）。改法：先强转 `(int)` 再用 `%d`。
4. **死字段**：`rg_touch_overlay.c` 里 `btns[i].is_toggle` 在 `rg_overlay_init()` 中从未被置真（开关早已改成程序化绘制 `blit_toggle`）。删掉或注明保留原因。

### 2.2 生命周期与悬空指针
5. **`lcd_deinit()` 不清 `tab5_fb`**：`mipi_dsi_tab5_p.h:379-389` 释放了 panel（帧缓冲随之失效）却留着 `tab5_fb` 指针；而 `tab5_batt_led_refresh()`（516）与 `tab5_perf_report()`（597）只判 `tab5_fb != NULL` 就往里写 → 应用切换窗口期存在悬空写。改法：deinit 里 `tab5_fb = NULL;`（一行）。
6. **`rg_input_deinit()` 只置标志、不等任务退出**：`rg_input.c:686-699`（等待循环被注释掉），而 `touch_handle` 被置 NULL → 之后输入任务的任何一轮 `rg_touch_ensure()` 都会因为 `touch_init_attempts < 20` 而**重新创建**触摸设备（在正在被 `rg_i2c_deinit()`/`rg_display_deinit()` 拆除的总线上），且新句柄再也不释放。改法：deinit 里把 `touch_init_attempts = RG_TOUCH_MAX_ATTEMPTS`（或加 `shutting_down` 标志），并考虑恢复"等任务退出"的等待（加上限）。
7. **INA226 设备句柄从不移除**：`rg_input.c:237` 只 `add_device`，全程没有 `i2c_master_bus_rm_device`。同一进程内反复进出游戏会累积（每次 ≤1 个句柄，实际影响很小，但属净泄漏）。

### 2.3 注释与实现漂移（本项目"照着注释做事"的实际风险源）
8. **90° 映射残留成片**：`mipi_dsi_tab5_p.h` 文件头（`(719-ly, lx)`、90CW）、`lcd_set_rotation()`（"旋转已固定在驱动里（90° CW）"）、`lcd_init()` 末尾日志（"90CW map"）都与实现（线性 `px=lx, py=ly`）矛盾；`rg_input.c:52`（"与显示驱动的 90° 映射互逆"）同理。
9. **`config.h` 顶部两块横屏口径**：`45-46`（"逻辑分辨率…驱动按 90° 映射写入，所以这里必须是横向的那一组数"）与 `58-79`（游戏区 `x[280,1000) y[120,600)` 的横屏 margin 推导）——与下方竖屏 `RG_SCREEN_VISIBLE_AREA {0,0,0,800}`、顶部 720×480 的实际布局冲突。
10. **电量换算注释与实现不一致**：`config.h:152` 引"官方口径 `(mv-3300)*100/(4150-3350)`"（分母 800），代码 `154` 用 `850`（=4150−3300）。当前实现自洽（4150mV→100%、3300mV→0%），但注释自称"杜撰不得"却与代码不同 → 未来校准会踩。
11. **FPS 文本坐标是横屏遗留**：`rg_touch_overlay.h:84-85` 的 `(640, 60)` 在竖屏下落在游戏画面内，仅因 `RG_OVERLAY_SHOW_FPS 0` 未暴露。
12. **`LCD_BUFFER_LENGTH` 注释**说"2 × 40KB"，实际 `720×32×2 = 46,080B`（≈2 × 45KB）；连带静态片内 SRAM 实际约 138KB（46K×2 + 48K stage）。

### 2.4 边界与并发（低概率，属加固）
13. **触摸命中用闭区间 + 整除半宽**：`rg_input.c:441-442`（`lx >= x - w/2 && lx <= x + w/2`），相邻命中区共享边界像素时两颗键会同时触发。当前布局每个方向都留了 ≥1px 间隙（`touch_layout.h`），属理论风险；改法：把右侧/下侧比较改成 `<` 或在命中后 `break`。
14. **去抖状态机对噪声形态敏感**：`rg_input.c:556-569` 的规则是"反向采样连续出现两次即采纳"。对实测的严格交替抖动（−871mA / +1mA 轮流）它恰好能压住（不会翻转），但只要真实噪声里出现**连续两次**同向反向采样（很常见），就会翻一次、回来又需两次 —— 表现为偶发单次闪烁。观感已被用户接受（v0.4.1 未再投诉），但想彻底稳，建议改成窗口多数表决：保留最近 8 次采样，≥6 次同向才改状态；或对电流值做长度 3 的中值滤波。
15. **`rg_batt_led_draw()` 无越界保护**：`rg_touch_overlay.c:960+` 直接按 `stride` 写 `buf`，信任调用方传整屏帧缓冲（当前唯一调用点满足）；`lcd_set_window()`（`mipi_dsi_tab5_p.h:392-401`）越界只告警不夹取。属"内部约定"，加一句断言即可。
16. **`alpha_level` 等静态量跨任务读写无同步**（设置菜单写入、显示/输入任务读取）：32 位对齐 int 的读写在本平台是原子的，不加锁可接受，但注释里应写明"故意不加锁，理由…"，避免后人误当 bug 加锁引入优先级反转。

### 2.5 双份实现 / 工具与固件漂移
17. **两个显示驱动文件长期双份**：763 行 vs 842 行、240 行实质差异（含横屏版残留的 PPA 压测代码）。本次 P1-1 就是它直接导致的。建议：把不用的那份删掉（结论留在文档），或把公共段抽头文件。
18. **PC 预览工具复刻了电量灯的几何与配色**：`tools/preview-touch-overlay.py:280-282`（`LED_R=12 / LED_CX=360 / LED_GREEN...`）与固件 `rg_touch_overlay.c:870-875` 是两份人工同步的常量（当前数值一致，已核对 360/12；色值未逐值比对，标"待确认"）。同时该文件的图注仍写着"绿：≥60%（**充电时闪的就是它**）"、"红：10~20%（<10% 会闪）"，**未反映 v0.4.1 的充电呼吸改动**，而这张图是要给用户看的。
   → 改法：图注改为"充电时呼吸的就是它"，并补一档"呼吸中间相位"的存证图；几何常量改为从固件源码解析（与键位表同样的做法）。
19. **刷机脚本无参数时仍会按时间取最新**：`tools/flash-retro-go.sh:26` `ls -t ... | head -1`（会打印告警）。点名纪律是"绝不 ls -t"；建议删掉这个分支，或改成必须显式 `--latest` 才允许。
20. **脚本的"写前核对分区表"只读不比对**：`read_flash 0x8000 0xC00 /tmp/dev_pt_now.bin` 之后没有任何比较逻辑，实际起不到核对作用（要么补比对，要么删掉这一步及注释）。

## 3. 已确认做对的地方（避免只挑刺）

1. **覆盖层合成位置正确**：放在"推给面板前的最后一刻"（两条路径都合），躲开了 GUI 立即模式重绘 → 不闪（历史 bug 27b44b4 的教训已固化在架构里）。
2. **CPU 路径的 cache 处理正确**：`esp_cache_msync` 只用 C2M（只写不读，无需 M2C 失效）；圆灯条带 offset 1,457,280 / len 40,320 与帧率带 offset 840,960 / len 161,280 **都是 128 的整数倍**（手算核对通过）。
3. **PPA 静默退回被治好**：源缓冲未 128 对齐时**显式告警一次**（这正是"白跑一整轮 A/B"的元凶）。
4. **电量读值不污染显示热路径**：I2C 只在输入任务里发生，显示路径只读缓存结构体。
5. **触摸懒加载 + 有限重试**（20 次 / 50ms 间隔）正确解决了 TP_RST 时序；命中条件的"看得见 + 建层成功"双条件（`visible && is_ready`）与"按键画不出来就不该点得到"严格同源。
6. **百分比换算有夹取**：`rg_input.c:335` 把 `RG_BATTERY_CALC_PERCENT()` 结果 clamp 到 0..100，挡掉了低电压时的负百分比。
7. **存档持久化分步走且顺序正确**：`memset(gamepak_backup, 0xff)` 在 `sram_load()` 之前、`sram_setup_path()` 纯字符串零 I/O；写入用 FNV 变化检测（不动就不写 SD）。
8. **键位表单一数据源**：`touch_layout.h` 同时被命中判定、可视层、PC 预览解析，三方不会漂移（这是本项目做得最正确的一处架构决策）。

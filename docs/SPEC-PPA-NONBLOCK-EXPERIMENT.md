状态：**已完成，结论见 `docs/PPA-NONBLOCK-RESULT-2026-10-10.md`**（2026-10-10 当轮跑完 A×2 / B×2 / C / D 四组）。
本文件保留为设计依据（纪律、判据、对照口径）；**结论与数据以 RESULT 文档为准**。
一句话：H1（阻塞等待是 25ms 的主因）**被推翻** —— 25ms 的真身是每块的叠加层合成（30.4ms/块），

- 临时测量钩子（`RG_GBA_DIAG` / `RG_TEST_KEYS_DEVICE` / `RG_TEST_MUTE` / `RG_TEST_NO_AUTOSAVE`）**交付前撤净**，实验期不出任何发行镜像。

## 1. 已经判死的形态（不重开，只引用）

| 形态 | 实测 | 出处 |
|---|---|---|
| 整帧一次 PPA | 16.8ms/帧 = **82MB/s**（= PSRAM 带宽地板）；CPU 对照 ~7.5ms | 经验沉淀 §125 |
| 按块 + **BLOCKING** + 写 DPI 帧缓冲 | **~25ms/块**（画面 1~2fps）；CPU 对照 0.6~0.9ms/块 | `PPA-RECORD-CORRECTION-2026-10-08.md` 第一节 |

**唯一没量过的自变量：传输模式。** `PPA_TRANS_MODE_BLOCKING` ⇒ `ppa_do_scale_rotate_mirror()` 不返回直到硬件搬完；
非阻塞 ⇒ 推入内部队列后立刻返回，完成时走 `on_trans_done` 回调。

## 2. 假设（可被证伪，这是本次唯一要回答的问题）

- **H1**：25ms/块里的主要成分是 **blocking 的等待/提交机制**，不是硬件本体。
  算术支持：一块 33 行 × 1440B = 47.5KB 进 + 47.5KB 出，在 82MB/s 下硬件只需 **≈1.2ms** ⇒ 25ms 里约 24ms 说不清。
- **H0**（反对假设，必须留）：25ms 就是 PPA 在这块板上「按块形态」的真实硬件成本（每 op 的固定延迟 + 与面板抢 PSRAM）。
  若成立 ⇒ 非阻塞只省下很小一段，**PPA 在本板按块形态彻底结案**，不再碰。

判据：模式 1 的「每块完成延迟（submit→done 回调）」若显著低于 25ms 且提交侧 CPU 成本下降 ⇒ H1 部分成立；
若完成延迟仍在 20ms 量级 ⇒ H0 成立。

## 3. 开关（唯一新增可变量）

`components/retro-go/targets/tab5/config.h` 新增编译期开关 `RG_TAB5_PPA_MODE`，**默认 0**：

| 值 | 含义 | 备注 |
|---|---|---|
| **0** | PPA 关（CPU 转置）—— **现状，默认，行为零变化** | 发行/日常用的就是这一档 |
| 1 | 按块 PPA **非阻塞**（新形态，本实验的主角） | 事件回调 semaphore + **1 深流水线** |
| 2 | 按块 PPA **BLOCKING**（= 当年 25x 那个形态） | **同配置对照**，隔离「等待成本」vs「硬件成本」 |

三档共用同一份提交/收块代码，只有 `.mode` 字段与“是否在提交后立刻返回”不同 ⇒ 满足「A/B 两次构建只差一个值」。

### 3.1 模式 1 的正确性要点（为什么不能只是把 mode 改一个枚举）

1. **源缓冲不可被覆写**：`lcd_send_buffer()` 收到的 `buffer` 由调用方逐块重填。非阻塞下硬件仍在读它 ⇒ 必须先把本块 `memcpy` 进**自己的 128B 对齐 PSRAM 暂存缓冲**再提交。
2. **流水线深度 1**：提交 op(N) 后立刻返回；**下一次提交前**先收 op(N)（等 semaphore）。深度 1 已足以回答 §2 的问题（把「等待发生在提交点上」变成「等待发生在下一块之前」），且不需要 ping-pong。
3. **叠加层必须推迟**：现在叠加层是 PPA 写完后由 CPU 写进同一片帧缓冲区域（`rg_overlay_blit_cw90(tab5_fb, …)`）+ msync。非阻塞下 PPA 可能还在写 ⇒ 会和 CPU 抢同一块像素。做法：提交时记下本块矩形，**收块之后**再合成叠加层 + msync；`lcd_sync()` 里把最后一块排空。
4. **失败必须说话**：任何 PPA 失败（含源未 128B 对齐）都要打日志并退回 CPU 转置，**绝不静默退回**（2026-09-25 白跑一整轮的元凶）。

## 4. 测量协议（口径与 P2-1/P2-2 基线对齐，这样数字能横向比）

- **负载**：GBA `恶魔城_晓月之圆舞曲`，脚本按键时间轴（与基线逐字相同：`8.0-8.3:A` 后每 6 秒一组），**300 秒**窗口，解析用 `--first 213` 固定窗口长度。
- **跑几组**：
  | 组 | 固件 | 跑次 | 目的 |
  |---|---|---|---|
  | A | 模式 0（现状） | 2 遍 | 基线 + **A/A 噪声底** |
  | B | 模式 1（非阻塞） | 2 遍 | 主实验 |
  | C | 模式 2（BLOCKING） | 1 遍 | 同配置对照（把 25x 复现出来并拆开） |
  C 组必须能复现出 ~25ms/块 —— 否则说明我没把当年那条路径调对，**整轮作废重来**（而不是拿一个「PPA 变快了」的假结论去报喜）。
- **指标**（全部取自 PERF/DIAG_FB 行，另加 PPA 三档打点）：
  1. 每块 **提交侧 CPU 时间**（`ppa_submit`）
  2. 每块 **完成延迟**（submit → done 回调，`ppa_done`）
  3. `display=Xms/s` 与 `[xpose= ovl= draw=]` 三段拆分
  4. 每秒推屏行数、推送次数/帧、每次行数（判断分块有没有被削碎）
  5. fps、丢块数、`previous draw operation is not finished` 条数、panic/WDT/复位
- **判读**：三组取同窗（`--first 213`）对照；A 组两遍给噪声底，差异小于噪声底的一律读作「无配置效应」。
- **交付**：原始日志（`.buildlogs/`）+ 解析表 + 结论（含 H0/H1 哪边成立、以及**对现有默认的影响 = 无**）。

## 6. 前置检查与风险

1. **SD 卡必须挂上**（没挂载 ⇒ 没 ROM ⇒ 什么都量不了）。先用一颗现成镜像刷一遍看启动日志里的挂载结果；若 `0x107` 超时 ⇒ 按基线文档 §5.1 处理（彻底断电 + 重插卡 + 上电）后再动。
2. **设备方向**：本实验在**横屏槽**跑（`launcher_l` / `gba_l`），刷完把引导槽设回 `launcher`（竖屏）——用户默认方向不被改动。
3. **settings/存档不受影响**：本次不动分区表、不动 nvs（`orient` 记录保持）。
4. **刷机**：沿用 `tools/flash-tab5-dual.sh <竖屏merged> <横屏目录>`（竖屏端可直接复用已经验收过的 `dist/orient-r3-portrait/`，只重编横屏），跑完用 `otatool.py switch_ota_partition --name launcher_l` 切到横屏开跑，收工再切回 `launcher`。
5. **成本**：一次横屏构建 ≈ 90 秒（实测 `.buildlogs/orient-s2-r3b-landscape.log` 09:36:38→09:38:09）；刷 + 跑一轮 ≈ 6 分钟 ⇒ 全程 ≈ 25 分钟机器时间。

## 为什么做竖屏

面板**原生就是 720×1280 竖屏**，而横屏版把逻辑画面做成 1280×720、在驱动里做 **90° 映射**
（= 逐行转置）。代价：内存**跳着读**（每 1440 字节只碰 64 字节），实测仅 28MB/s，
而顺序读可达 89MB/s → 这是 `transpose=` 那段 **6~8ms/帧** 的来源，也是显示通路里最贵的一项。

**竖屏下逻辑画面 = 720×1280 = 物理布局 → 映射退化为恒等 → 读写全部顺序化** ✓
预期 `transpose=` 掉到 ~1ms，足以让总开销跨进 60fps 的 16.7ms 预算。

## 关键事实（已核实，别搞错）

- 核心输出 **240×160**，缩放 **3× 整数 = 720×480**
  → **竖屏下游戏画面尺寸与横屏完全相同（720×480）**，只是位置从"居中两侧留白"变成"顶部"
  → 不存在"画面变小"的代价 ✓
- 竖屏布局：`y=0..480` 游戏画面（满宽 720）· `y=480..1280` 控制区（**800px 高**，
  对比横屏两侧各 280px 宽 → 触摸区域大幅改善 ✓）
- 面板与 BSP **本来就是竖屏配置**，**不需要动面板、不需要动 BSP** ✓

## 手术点（已精确定位，2026-09-27 侦察结果）

驱动文件 `drivers/display/mipi_dsi_tab5.h`（764 行）结构：

| 行 | 内容 |
|---|---|
| 77-78 | `TAB5_PHYS_W 720` / `TAB5_PHYS_H 1280`（面板物理竖屏） |
| 199 | `tab5_draw()` |
| 373 | `lcd_set_window()` |
| **580** | **`lcd_send_buffer()` ← 热路径，转置就在这里面** |
| **594** | **`const int x0 = TAB5_PHYS_W - tab5_win_top - rows;` ← cw90 映射核心**（逻辑行 → 物理列 x） |
| 691 | `rg_overlay_blit_cw90(tab5_scratch, rows, x0, y0, rows, w, TAB5_PHYS_W)`（叠加层块） |
| 729-730 | cache 写回范围 `((size_t)y0 * TAB5_PHYS_W + x0) * 2` ← **物理寻址，必须跟着新映射一起改** |
| 737 | `rg_overlay_blit_cw90(tab5_fb, ...)`（整层叠加，含帧率数字） |

### 要改什么（线性行映射）

1. `lcd_send_buffer()` 里的**目标寻址**：由"逻辑行 → 物理列"（cw90）改为
   **"逻辑行 → 物理行"**（线性），并加上竖屏布局的 y 偏移（游戏画面放 y=0..480）。
2. **第 729-730 行的 cache 写回范围**必须同步改成新的物理寻址（否则写回错区域，
   会出现上次"直写蓝屏"那类问题）。
3. 叠加层：`rg_overlay_blit_cw90` 需要一个**线性版本**（竖屏下 UI 不再旋转），
   或让调用点走线性路径。
4. `config.h`：逻辑分辨率改 **720×1280** + 指向本 target 自己的驱动编号（新驱动文件）。
5. ⚠ **1~4 必须同时落地** —— 只改分辨率会显示全乱（横屏 E2 的教训）。

### 已验证的既有事实（别重复踩）

- 面板与 BSP **本来就是竖屏**，不需要动面板/BSP ✓
- 核心输出 240×160、3× 整数缩放 = **720×480** → 竖屏下游戏画面尺寸与横屏**完全相同** ✓
- 缩放/滤镜逻辑（`filter_x` / `map_viewport_to_source_x`）在 `rg_display.c` 里，与旋转无关，**不用动** ✓

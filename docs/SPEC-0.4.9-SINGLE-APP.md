# SPEC · 0.4.9 单 app（一份镜像 = 启动器 + 双核 + 横竖屏）

状态：**待评审**（只写设计，不动手；评审通过后排期）
作者：Hermes（受 2026-10-10 决策驱动）
前置阅读：`docs/SPEC-S2-ORIENTATION-SWITCH.md`（双 app 形态的来源）、`docs/PPA-DECISIONS.md`

---

## 0. 一句话目标

**0.4.9 = 一个 app。** 一次刷机、一个发布包；启动器里选方向；横竖两个方向、两套模拟器核心、菜单 UI 全在同一份镜像里。
不再存在 "launcher / 横屏 / 竖屏" 的槽位拆分，也不再有 `_l` 后缀分区。

---

## 1. 为什么（收益，按重要性）

1. **一个构建 = 一个版本。** 消灭版本漂移：现在竖屏 r3 / 横屏 r4 就是两代镜像（今天的实测也印证了这种维护摩擦）。
2. **发布简单且安全。** M5Burner 只需一个包；**"拿错方向的 merged 直接刷会覆盖掉相邻分区前 64K"（P3 隐患）在单 app 下自然消失**。
3. **分区表回归常规**，空间余量大：16MB flash，单 app ≈3.5MB，A/B 双槽 ≈7.4MB ✓
4. **用户概念更少。** "方向 = 另一个 app" 对用户是个不必要的负担；单 app 后方向只是启动器里的一个设置项。

---

## 2. 现状（全部为实测值，非估计）

| 项 | 实测 |
|---|---|
| flash | **16MB**（真机启动横幅 `SPI Flash Size : 16MB`） |
| 当前形态 | 双 app：**6 个 app 槽**（`launcher`/`retro-core`/`gbsp` × 竖、`*_l` × 横），app 区 0x10000–0x760000 = **7.0MB** |
| 各二进制（横屏档） | `launcher` 854KB、`retro-core` 1450KB、`gbsp` 1209KB ⇒ 合计 **≈3.42MB** |
| 方向耦合面 | `RG_TAB5_ORIENTATION` 全项目 **13 处 / 2 个文件**（`targets/tab5/config.h` 3 处 `#if`、`touch_layout.h` 2 处 `#if`） |
| 编译期几何常量 | `RG_SCREEN_WIDTH/HEIGHT` 共 94 处，但**非 target 文件只有 3 个**：`rg_display.c` 13、`rg_touch_overlay.c` 11、`rg_touch_skin.c` 4。**GUI/菜单/模拟器核心不碰它** |
| 两份显示驱动 | `mipi_dsi_tab5.h`(71KB 横屏) / `mipi_dsi_tab5_p.h`(57KB 竖屏)，**定义完全相同的一整套符号**（`lcd_init`/`lcd_sync`/`tab5_draw`/…）⇒ 目前是 `rg_display.c:153/155` 二选一 include |
| **单 app 形态** | **已实现、有构建开关**：`-DRG_SINGLE_APP=1`。落点：`launcher/CMakeLists.txt`、`launcher/components/gbsp-core/`、`launcher/components/retro-core-main/`、`base.cmake:43`、`components/retro-go/CMakeLists.txt:74`、`rg_tool.py:277`（`--single-app`）。当前构建缓存里 `RG_SINGLE_APP=0`（关着） |
| 单 app 的进/出核心机制 | 已实现：NVS 待续标志 `rgapp/core`（`rg_system.c:172-230`）+ 重启；`1` = GBA(gbsp) 单核入口，`2` = retro-core 多核分发器；空 = 回菜单 |
| 存档落点 | **SD 卡**（`RG_BASE_PATH_SAVES`）⇒ **换分区表不会丢存档**，只会丢 NVS 里少量设置 ⚠（更正此前"重刷丢存档"的说法） |
| 当前方向真值 | **运行分区标签**（`rg_orient_running()` / `rg_orient_app_label()`）⇒ **单 app 下标签不再携带方向，必须改成设置项** |

**核心判断**：单 app 这件事**不需要从头造**——分发器、双核心同编、进/出核心的待续标志都已存在且在跑。0.4.9 的**新增工作集中在"把方向从编译期+双分区，改成运行时+单分区"**这一件事上。

## 3. 目标架构

```
一个 app（预估 3.6–3.8MB；A/B 双槽各 4MB）
├── 分发器（复用现成 RG_SINGLE_APP 逻辑）
│    ├── launcher（菜单 / 设置 / ROM 列表）
│    ├── gbsp（GBA 单核心）
│    └── retro-core（多核心：gb/gbc/nes/pce/sms/gg/col/gw/snes/lnx）
├── 显示后端 A：横屏驱动（物理 720×1280 + 90° 映射）
├── 显示后端 B：竖屏驱动（物理 720×1280 原生）
├── 键位表 × 2（已同文件）、皮肤底图 × 2（需同编 + 运行时选）
└── 方向 = 运行时设置（NVS/SD），启动时决定用哪个后端
```

**切换语义（v1，刻意保守）**
- **换方向**：写设置 → `esp_restart()` → 分发器按设置初始化对应的显示后端。
  （不做运行中热切换：DSI + PPA + 触摸 + LVGL 整体重初始化风险高，留给 v2 评估。）
- **进/出游戏**：沿用已实现的"写 NVS 待续标志 + 重启"。不做进程内热启动，因为核心隐含假设"自己是从干净启动起来的"（静态初始化、堆布局、一次性资源）。

## 4. 工作项（文件级，分"必须"与"可选"）

### 4.1 显示层：两份驱动共存 ← **核心工作量**
- **W1** 给其中一份驱动加符号前缀（建议竖屏：`mipi_dsi_tab5_p.h` 的 `lcd_*`/`tab5_*` → `*_p`），**不改内部逻辑**。
- **W2** 新增薄分发层 `drivers/display/tab5_dispatch.h`：`lcd_init`/`lcd_sync`/`lcd_set_window`/`lcd_set_rotation`/`lcd_set_backlight`/`lcd_deinit`/`tab5_draw`/`tab5_perf_flush`/`tab5_axi_icm_tune`… 各转一次，按运行时方向选后端。
- **W3** `rg_display.c:153/155` 的二选一 include → 同时 include + 只走分发层。
- **W4** **保证只有生效的那一份做 init**：两份驱动各自持有帧缓冲/PPA client/window 状态；必须验证不会"两份都 init ⇒ 多占一块 1.8MB 帧缓冲"。
- 风险：两份驱动对同一硬件的假设不同（竖屏 = CPU 转置路径；横屏 = PPA/CPU 转置 + 90° 映射 + 条带窗口）。分发层**只包接口，不试图统一内部**。

### 4.2 方向：编译期 → 运行时
- **W5** `targets/tab5/config.h` 3 处 `#if`（`RG_SCREEN_DRIVER` 2/3、屏幕尺寸、条带参数）→ 改成按运行时方向查表；
  **保留 `-DRG_TAB5_ORIENTATION=` 作为开发期"强制单方向"开关**（用来隔离调试某个方向的显示代码——这是对"失去风险隔离"的补偿）。
- **W6** `touch_layout.h` 两张键位表 → 按运行时方向选表（两张表已在同文件里，改动很小）。
- **W7** `rg_display.c`(13) / `rg_touch_overlay.c`(11) / `rg_touch_skin.c`(4) 的几何常量 → 统一改读运行时视口。
- **W8** 皮肤/布局资产：两套底图同编 + 运行时选。**横屏底图属 GUI 改动 ⇒ 必须先生成同源预览图给你确认，不得自行豁免。**

### 4.3 方向真值与切换
- **W9** `rg_orient.c`：`rg_orient_running()` 从"读分区标签"改为"读设置项"；切换从 `esp_ota_set_boot_partition` 改为"写设置 + `esp_restart()`"。
- **W10** `rg_system.c:265-289` 的 `rg_orient_app_label()` 分支在单 app 下失效 → 用 `#if RG_SINGLE_APP` 分流（与现成单 app 分支并列，**不动现有双 app 路径**）。
- **W11** 真源唯一：方向只存 `ui.json`（namespace `ui`、key `orient`），单 app 下它就是唯一真值（不再可能与分区标签冲突）。
- **W12** 失败兜底：显示后端 init 失败 → 记一行日志 + 回落另一方向（防"选错方向就黑屏出不来"）。

### 4.4 分区表与发布
- **W13** 新增单 app 分区表 `tools/partitions-single-tab5.csv`：`app0(4MB, ota_0)` + `app1(4MB, ota_1)` + nvs/otadata/phy（+ 可选 spiffs）；总占用 ≈8.2MB ✓
- **W14** `rg_tool.py` 的 merged 生成改用这张表，并**顺带修掉 P3**：内嵌分区表必须来自真源 CSV（现在按当次二进制体积生成 ⇒ 会与真源不一致）。
- **W15** 发布口径：0.4.9 = 首个单 app 版；M5Burner 一个包；说明写清"从 0.4.8 / 双 app 版升级 = 整机重刷（**存档在 SD，不受影响**；丢失的是 NVS 里的少量设备设置）"。
- **W16** 门禁 `tools/check-single-partition.py`：刷机前断言 merged 内嵌表 == 真源 CSV（扩展/替代 `check-dual-partition.py`）。

## 5. 验收判据（可机检，不靠感觉）

1. **只刷一个 merged** → 起来进启动器；选横/竖各重启一次，两个方向都能：进 GBA 游戏、进一个多核游戏、**触摸虚拟按键落点正确**（横屏判据 `90CW map`、竖屏 `linear 1:1 map`）。
2. **横屏性能不退化**：`PERF: display=` 每块 ≈1.05ms、游戏 57–60fps、`drops=0`（与 r4 基线**同一套钩子**对照）。
3. **竖屏行为零变化**（与 r3 基线逐项对照，含触摸、存档、电源）。
4. **镜像体积 ≤4MB**；分区表断言通过；`find -newer` + sha256 断言"刷的就是刚编的"。
5. **设置持久化**：断电重启方向不变；SD 卡换到另一台同版设备方向跟着走。
6. **存档不受影响**：横竖切换前后 `.sav` 正常读写（同一 SD 路径）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| **失去风险隔离**（今天"P0 崩横屏、竖屏照跑"的性质没了） | 保留 `-DRG_TAB5_ORIENTATION=` 开发期单方向构建；W12 兜底；每期都做"两方向冒烟" |
| 分发层的隐蔽耦合（两份驱动对硬件假设不同） | W4 明确只 init 一份；真机前后各一次两方向进游戏冒烟 |
| 二进制增大（两份驱动 + 两套皮肤） | W13 槽位按 4MB 留足；每期复核 app 槽余量 |
| 发布后回退变难（分区表变了） | 发布说明写清；保留 r3/r4 双 app 镜像做回退路径，并写明"降级需刷回旧 merged（分区表随之回退）" |
| 单 app 变大后编译变慢（每次都要编两个核心） | 开发期用 `-DRG_TAB5_ORIENTATION=` + 只编需要的核心（若 rg_tool.py 支持） |

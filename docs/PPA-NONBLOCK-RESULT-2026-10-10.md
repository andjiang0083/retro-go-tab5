# PPA 按块传输模式实验结果（2026-10-10）

**一句话结论：历史「按块 PPA 慢 25 倍」不是 PPA 本体慢，也不是 blocking 等待 —— 而是每块都要执行的
「虚拟按键叠加层合成」：它 (a) **每块都把全部 13 个按键（≈1.36e5 像素）在 PSRAM 帧缓冲上重新混合一遍**
（裁剪矩形传的是"整屏"，而 blit 的循环体是「按键矩形 ∩ 裁剪矩形」⇒ 等于没裁剪）、(b) 做两次跨度约
**1.03MB** 的 `esp_cache_msync`。把这一段跳过之后，PPA 本体每块只要 **0.41ms**，比现行 CPU 转置
（1.06ms）**快 2.6 倍**。⇒ 「PPA 只能用整帧一次」这条既有结论的**前提被推翻**，必须重算。**

> **⚠ 2026-10-10 晚更正（第一版说错了一处）**：本文最初写「整屏矩形**遍历 92 万像素**」——
> 不准确。`blit_one` 的循环体是「按键矩形 ∩ 裁剪矩形」，传整屏**不是**遍历整屏，而是**不做任何
> 额外裁剪 ⇒ 每块混合全部按键**。量级从 9.2e5 修正为 1.36e5（13 个按键的矩形面积之和），
> 量级仍与实测 30.4ms/块 吻合（≈0.2µs/px，PSRAM 读改写）。机制结论不变：**问题在裁剪矩形**。
> 修法与实测见 §6。

- 实验设计：`docs/SPEC-PPA-NONBLOCK-EXPERIMENT.md`
- 代码开关：`RG_TAB5_PPA_MODE`（0=PPA 关/默认，1=非阻塞+1 深流水线，2=BLOCKING），横屏驱动专用
- 日志：`.buildlogs/ppa-{A-mode0,A-b,B-mode1,B-b,C-mode2,D-mode2-skipoverlay}-serial.log`
- 分析脚本：`~/.hermes/cache/scratch/analyze-ppa.py`（按负载分档，见下）

## 1. 测量口径（先说清，否则数字会被误读）

**负载是分段的**：attract demo 前 ~120 秒是标题画面（~35 块/秒），之后才是全屏变化的 demo
（~360 块/秒）。两者差 10 倍，混在一起平均等于拿轻载比重载 ⇒ 一律**按「每秒推送块数」分档**比较。

**A/A 噪声底**（同一颗镜像跑两遍，A1 vs A2）：

| 档 | A1 每块 | A2 每块 | 离散 |
|---|---|---|---|
| 低载 10–80 块/秒 | 1.17ms | 1.12ms | 4% |
| 中载 80–250 块/秒 | 0.98ms | 0.96ms | 2% |
| 高载 250–450 块/秒 | 1.06ms | 1.07ms | 1% |

⇒ 噪声底 ≤4%，**差别超过 5% 才算真差别**。CPU 转置每块代价**跨 10 倍负载恒定**（0.96–1.17ms），
所以"每块代价"本身可以跨负载引用。

**⚠ 口径陷阱（差点误判）**：`PERF: display=` 只统计**计时窗口内**的 CPU 时间。
- CPU 转置路径（mode 0）：全部开销都在窗口内 ⇒ `display/blocks` 就是真实每块代价。
- PPA 路径（mode 1/2）：**收块等待发生在 `lcd_get_buffer()`（窗口之外）**，叠加层合成在 mode 1 下也被
  推迟到窗口之外 ⇒ 光看 `display` 会得出"PPA 只要 0.3ms/块"的**假便宜**。
  真实口径：mode 1 = `ops/s ×(sub_avg+wait_avg)`；mode 2 = `transpose + submit` 两段之和。
- `PERF` 行里三个计数器（第 981–1000 行）语义：`t_tr1` 之前 = `transpose`，`t_tr2-t_tr1` = `submit`，
  **而 `submit` 这一段就是叠加层合成**（见 §3）。

## 3. 根因

`tab5_ppa_compose_overlay()`（`mipi_dsi_tab5.h:464`）在**每一块**推送后执行，含两处近全屏量级的开销：

1. **每块重混全部按键**（第 501 行，2026-10-10 晚更正后的机制）：
   ```c
   rg_overlay_blit_cw90(tab5_fb, TAB5_PHYS_W, 0, 0, TAB5_PHYS_W, TAB5_PHYS_H, TAB5_PHYS_W);
   //                                             ↑ 裁剪矩形 = 整屏 ⇒ 等于不做裁剪
   ```
   `blit_one()` 的循环体 = **「按键矩形 ∩ 裁剪矩形」**，所以传整屏的后果是
   **每块都把 13 个按键（≈1.36e5 像素）在 PSRAM 帧缓冲上读改写一遍**（≈0.2µs/px → ~27ms/块）。
   对照：CPU 路径传的是**本块矩形**（`..._cw90(tab5_scratch, rows, x0, y0, rows, w, ...)`），
   只混合落在本块内的按键 ⇒ 实测 `ovl` 仅 **3ms/s**。
   **两边差的不是"朝向"，是"裁剪矩形"** —— 这一点第一版写错了。
   想直接在帧缓冲上裁剪是**做不到**的：blit 把 `(rx,ry)` 当**缓冲原点**（传 `(x0,y0)` 会整体偏移，
   源码注释里记着这个坑）⇒ 正解是把合成搬到"原点天然=本块"的**源缓冲**上（P0，见 §6）。
2. **近全屏 cache 维护**（第 476–503 行）：`b0/b1` 由"块内首像素→末像素"的线性字节偏移算出。
   而一个 27 行 × 720 的**列带**在帧缓冲里的线性跨度 = 从 `(y0*720+x0)*2` 到 `((y0+719)*720+x0+26)*2`
   ≈ **1.03MB**（帧缓冲总量 1.8MB 的 57%）。**每块两次**（先 `M2C` 失效、后 `C2M` 写回）。

⇒ 每块约 28ms。**2026-10-10 晚用分段计数定案（C2b 组，34.8 块/秒档）**：
**26.8ms 是"按键混合"**、**0.37ms 是 cache 维护**（96% : 1.3%）—— 与 msync、与 PPA 旋转、
与传输模式（blocking/non-blocking）、与 PSRAM 带宽争用**都无关**，这是本次实验最重要的更正。
真身一句话：**每块都把 13 个按键（≈1.36e5 像素）重混一遍**（因为裁剪矩形传成了整屏）。

### 对既有判断的修正

`mipi_dsi_tab5.h` 第 315–331 行原注释的结论是：「PPA 要用就**整帧一次**用，绝不能按块用」，
理由是「每条带子单独发一次阻塞 op」+「PPA 写帧缓冲与 DPI 扫描抢 PSRAM 带宽」。

实测：
- **阻塞 vs 非阻塞只差 0.3ms/块**（591µs vs 274µs 提交；等待 0 vs ~1.1ms）——把等待挪到窗口外，
  总代价从 30.4ms 降到 1.4ms，**降幅 95% 来自"叠加层跟着搬走"，不是"传输模式变了"**。
- PPA 本体（0.41ms/块）**快于** CPU 转置（1.06ms/块）。
⇒ 「整帧一次」这条结论的前提不成立；要不要走整帧路线，必须用修好叠加层之后的数重新推导。

## 6. P0：把叠加层合成搬到源缓冲（`RG_TAB5_PPA_MODE=3`，2026-10-10 晚）

### 6.1 为什么是这个修法（不是"换朝向"）

- 想让旧的"帧缓冲直写"变便宜是**做不到**的：blit 把 `(rx,ry)` 当**缓冲原点**，传 `(x0,y0)` 会让画面整体偏移
  （源码注释里记着这个坑）⇒ 唯一办法是合成到"原点天然=本块"的缓冲上。
- 于是 mode 3 = 取本块 → **换序拷贝**进暂存块（`tab5_stage`，48KB，实测在 internal DRAM `.dram0.bss` 0x4ff13a00）
  → `rg_overlay_blit(tab5_stage, w, win_left, win_top, w, rows)`（**逻辑朝向**合成，随旋转被 PPA 一起转过去）
  → PPA 改用 `.byte_swap=false`（暂存块已换成小端）+ 源换成暂存块。
- 落点等价性：`blit_one` 的 cw90 变换 `bx0 = phys_w - y - h` 与驱动 `ly → px = (phys_w-1)-ly` 是同一变换
  ⇒「逻辑合成 + PPA 旋转」与「物理合成」逐像素等价（构造上等价，仍需真机肉眼确认按键落点）。
- **不碰帧缓冲** ⇒ 没有那两次 `esp_cache_msync`、也不与 DSI/PPA 抢帧缓冲。

### 6.2 实测（`dist/p0x-*`，240s/档，attract demo，与 A 组同一套钩子）

| 档 | 每块 | 叠加层拆账 | 判断 |
|---|---|---|---|
| A2 = mode 0（CPU 转置，基线） | 高载 **1.05ms**、display 380ms/s | — | 与历史 A 组（1.06ms / 384ms/s）逐项一致 ✓ 基线可信 |
| C2b = mode 2（帧缓冲合成） | 低载 **27.86ms** | `ovl_blit` **26.8ms** / `ovl_sync` **0.37ms** | 真身定案：混合占 96%，msync 可忽略 |
| E2 = mode 3（源缓冲合成，SPAM=1） | **4.26ms**（且只有 47 块/10s） | `stage` 3.87ms（换序拷贝 0.46ms ⇒ **混合仍 3.4ms**） | 未达标；且游戏卡死 |
| E3 = mode 3 复测（SPAM=0 干净日志） | 显示路径**达标：0.91ms**（`stage` 503µs：混合仅 44µs） | 同上 | **系统级崩塌**：240s 只推进约 6s 的量 ⇒ **判定 mode 3 失败** |
| F4 = mode 3 + **补回每块两次 msync**（只差这一个变量） | 显示路径同样达标（`ovl_sync` **仅 15µs**、PPA 每条 391–509µs） | — | **与 E3 逐项相同**（心跳 6 行 / 提交 150）⇒ **msync 不承重** |

**E2/E3 的硬伤（如实记录：mode 3 判定失败）**：
- **E2**（`SPAM=1`）：游戏停在 `f=15`，日志断流 → 当时首要嫌疑是"每帧 130 行 UART 把日志路径卡死"。
- **E3**（`SPAM=0` 干净日志，`dist/p0y-E3`）：**同样崩塌** —— 240s 里 `DIAG_TEAR` 心跳只有 **6 行**
  （A3 基线 225 行、C3 对照组 202 行），即模拟器只推进了约 6 秒的量（≈2.5% 速度）。
  ⇒ **UART/日志嫌疑被推翻；这是 mode 3 自身的真问题。**
- **但显示路径本身是达标的**：E3 稳态每块 **0.91ms**（`stage` 503µs，其中**叠加层混合只剩 44µs**、
  换序拷贝 459µs），窗口 1 那个 3.4ms 的混合是**开局一次性瞬态**（首屏推全屏）。
- 已排除：UART 刷屏、PPA 输入对齐、`tab5_stage` 存储落点（`nm` 实测 internal DRAM）、按键写入越界。
- **未解规律（不猜，留作下次第一优先）**：**"每块不再碰帧缓冲"与崩塌强相关** —— 当年 D 组（跳过帧缓冲合成）
  同样掉到 ~2fps，两者唯一共同点就是去掉了每块那两次帧缓冲 `esp_cache_msync`。
  ⇒ 假设：那两次 msync（或其带来的 cache 行为）是**承重的**。**验证办法**：保留 msync、只去掉像素混合
  （若仍然快 ⇒ msync 承重，则 P0"省 msync"这条路根本不存在，P0 全线作废）。

**自我更正（本轮第二次口径翻车）**：中途我曾用新加的 `gap_avg`（相邻两次 send 的间隔）判"调用方慢 0.5s/块"，
但**A3 基线自己的 `gap_avg` 也有 69ms–3.4s 的窗口** ⇒ 该指标被异常值污染，不能单独用来指认卡死。
最终改用 **`DIAG_TEAR` 每秒心跳**（不受 SPAM 影响）才定案。**教训：新指标先拿基线做对照，再解读。**

### 6.3 结论与当前状态

- **P0 首版（mode 3）判定失败**，已按纪律**整笔回退**：默认 `RG_TAB5_PPA_MODE` 保持 0
  （发行/日常行为与 r3 逐字一致），mode 3 代码保留但打上"⛔ 受试失败，不要用"注记
  （含失败数据、已排除项、待验证假设），仅用于将来复现该异常。
- **没有在失败点上叠加修复**。F4 已经做完了那次分辨：**补回 msync 完全无效**（与 E3 逐项相同）
  ⇒ "msync 承重"这条假设**被证伪**，P0"省 msync"的账面讨论到此为止（不需要再算 1.28ms 那笔账）。
- **现在剩下的硬事实与唯一未排除项**：
  - 硬事实：**因果在显示路径、成本不在显示路径** —— 10s 窗口里显示只占 2%（`stage` 503µs、
    `ovl_sync` 15µs、PPA 每条 ~0.4ms），可系统只有 0.63 提交/秒（A3 31/s、C3 2.4/s）。
  - 未排除的结构差异只剩一条：**PPA 的输入从行缓冲换成了暂存块 + `.byte_swap=false`**
    （mode 2 读行缓冲 + 换序）。**一次二分就能定案**：
    `mode 5 = mode 2（叠加层仍合成进帧缓冲）但 PPA 输入走"换序拷贝进暂存块 + byte_swap=false"`。
    - 若 mode 5 也崩 ⇒ 罪魁是**PPA 的输入配置**（与叠加层搬到哪儿无关）。
    - 若 mode 5 正常 ⇒ 罪魁是"**CPU 不再混帧缓冲**"这件事本身（F4 已排除 msync，所以不是 cache 维护）。
  - **不建议在没定案前继续投时间**：P0 的最好情形收益也只有 ≈20% 显示路径（≈8% CPU），
    而账面上它已经吃掉三轮实验、三个被证伪的假设。**建议挂起**，等有真实掉帧的重游戏再说
    （横屏现已跑满 60fps，"省 CPU"换不回帧率）。
- **`RG_TAB5_PPA_MODE` 允许的取值范围**：0（默认/现状）、1（非阻塞，实测更贵，仅供复核）、
  2（BLOCKING 对照，27.86ms/块）、3（受试失败）。
- **本次唯一的净收益仍是"归因"**：把"按块 PPA 慢 25 倍"从"PPA/带宽问题"钉成
  **"每块重混 13 个按键（26.8ms）+ msync 可忽略（0.37ms）"**，并就地更正了旧注释与旧结论文档。

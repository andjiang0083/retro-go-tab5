# Tab5 显示通路 · 基线（P2-1）

> 目的：在动显示通路之前，先把「每帧平均脏行数」「推屏 fps」两个数字用**真机数据**钉住，
> 后面所有优化都跟这份基线比，不靠感觉。原始数据见 `docs/baseline/display-path-A-raw.txt`。

## 一、结论速览

| 指标 | A 组（开关 OFF = 改动前行为） |
|---|---|
| 推屏帧率 | **60.0 fps**（= 游戏自身节奏，GBA 约 59.7fps） |
| 每帧平均脏行数 | **147.6 行/帧**（整屏 720 行，约 **20.5%** 的行每帧会变） |
| 每帧平均推送块数 | **5.24 块/帧**（块 = 32 行 ⇒ 实际推 **≈168 行/帧**） |
| 显示通路占用 | **271.8 ms/s**，即每秒钟约 **27.2%** 的时间花在把画面送上屏 |
| ├ transpose（字节序/旋转） | 123.3 ms/s |
| ├ draw（行拷贝/像素搬运） | 140.7 ms/s |
| ├ overlay / submit | 6.4 / 0.2 ms/s |
| 丢块 | **0 / 62616**（0.0%） |
| 单次推送行数 | 平均 33.16 行，单次最大 84 行 |
| 采样窗口 | 199 秒 / 11940 帧 |

参考（同一台设备、**启动器空转**时，另一轮 330 秒采集）：`display=1.75 ms/s`、`blocks=2/秒`、`rows=32 max=32`。
即：**空转时显示通路几乎不花钱，成本全部来自游戏画面的逐帧变化**。

## 二、这两个数字说明了什么

1. **显示通路是第二大开销**：一秒钟里有 0.27 秒在做「把画面送上屏」，其中 transpose（字节序/旋转）和 draw（行搬运）各占一半。
2. **现在的推送粒度已经是 32 行了**：一帧平均只推 5.24 块，而理论上"只推变化行"需要 `147.6/32 ≈ 4.6` 块。
   换句话说，**块级推送已经吃到了行级下限的约 88%**——因为 GBA 画面变化是成片的（卷动、动画），脏行本来就抱团。
3. **由此可以先算出 P2-2 的收益上限**（避免事后吹）：
   - 行级推送最多把「推 168 行」降到「推 147.6 行」⇒ 省约 **12%** 的推送量；
   - 折算到壁钟时间：`27.2% × 12% ≈` **1.7% 的每帧时间**。
   - 也就是说：**P2-2 不会让 fps 从 60 变成 120**（fps 由游戏节奏决定，本来就不是瓶颈），它的价值是
     **省出约 1.7% 的 CPU 时间 + 减少推送事务数**。达不到就照实写「未达标」，不调低目标。
4. **帧率目标（≥30fps）本身早就满足**：60fps 是游戏节奏，显示通路再差也很少掉下来；真正有意义的是
   「连续 2 小时不 wedge」这条稳定性门槛，以及省下来的时间。

## 二之二、A/B 实测（P2-2「只提交变化行」）

同窗（约 200 秒 / 12120 帧）、同 ROM、同按键时间轴；两份固件**只差一个编译期开关值**，
B 组日志里有自证行 `display: 只提交变化行 = 开（编译期默认 1，SD 开关 无）`。

| 指标 | A（关） | B（开） | Δ |
|---|---|---|---|
| 推屏 fps | 60.0 | 60.0 | 0% |
| 每帧平均脏行数（内容） | 147.6 | 141.1 | −4.4% |
| **每秒实际推屏行数** | **10061** | **8803** | **−12.5%** |
| 相对"只推变化行"理论下限的浪费 | +13.6% | **+4.0%** | — |
| 推送次数/帧 | 5.24 | 5.52 | +5.3% |
| 每次推送行数 | 33.16 | 26.58 | −19.8% |
| 每行代价（display 内） | 27.02 µs | 28.03 µs | +3.7% |
| **display 通路占用** | **271.8 ms/s** | **246.8 ms/s** | **−9.2%** |
| ├ transpose | 123.3 | 104.4 | −15.3% |
| ├ draw | 140.7 | 134.4 | −4.5% |
| 丢块 | 0 / 62616 | 0 / 66912 | 0 |
| 复位 / panic / WDT | 0 | 0 | — |

**结论（before → after）**：推屏行数 **10061 → 8803 行/秒（−12.5%）**；显示通路 **271.8 → 246.8 ms/s（−9.2%）**，
折合每帧时间**省 25.0 ms/s ≈ 2.5%**；fps 不变（60，由游戏节奏决定）；0 丢块。

**必须一起写出来的三条保留意见**：

1. **fps 没有提升，也不该有**：60fps 是游戏节奏，显示通路不是瓶颈。真实收益是"每秒省 25 ms 的 CPU"。
2. **有内容混淆项**：两次窗口的脏行数差 4.4%（147.6 vs 141.1），所以 −9.2% 里可能有一小部分来自内容差异；
   按"每行代价"看，B 反而略贵 3.7%（推送次数变多、每次更碎），**收益的来源是推得更少（−12.5%），不是推得更快**。
3. **事先写好的 12% 上限被实测印证**（−12.5% 推送量），但我原先折算的"≈1.7% 每帧时间"偏保守，
   实测 **2.5%**——同一量级，不是倍数级。

## 三、采集方法（可复现）

```sh
# 1) 固件：诊断构建（P2-1/P2-2 临时钩子，验证完回退）
#    - RG_GBA_DIAG=1 / RG_GBA_DIAG_SPAM=1  → 每秒打 PERF，每 60 帧打 DIAG_FB
#    - RG_TEST_NO_AUTOSAVE=1               → 禁 SD 自动写，避免污染计时
#    - RG_TEST_KEYS_DEVICE=<时间轴脚本>     → 无人值守按键（8.0-8.3 按 A；之后每 6 秒换一组方向+A/B）
#    - 启动器侧 rg_test_auto_boot_rom()     → 开机直接进 /sd/roms/gba 下第一个 .gba（免菜单导航）
cd ~/esp32/retro-go-tab5 && . tools/idf-env.sh
cd retro-go-p4 && python3 rg_tool.py --target tab5 --no-networking build-img launcher gbsp
cd .. && sh tools/flash-tab5.sh retro-go-p4/retro-go_<ver>_tab5.img 330 > /tmp/p21-A.log 2>&1

# 2) 解析（算每帧脏行数、推屏 fps、显示占用）
python3 ~/.hermes/cache/scratch/parse_p21.py /tmp/p21-A.log
```

- **A/B 可比性**：A、B 两次构建只差「变化行开关」一个值，ROM、按键时间轴、采样窗口完全相同。
- **按键时间轴**：`8.0-8.3:A` 之后每 6 秒一组（`RIGHT|A`,`LEFT|A`,`DOWN|A`,`UP|A`,`RIGHT|B`,`LEFT|B`,`DOWN|A`,`UP|B`），
  A 组覆盖到 302 秒，B 组延长到 1800 秒（**前 300 秒与 A 逐字相同**，保证对比窗口一致）。

## 四、现场注意事项（踩过的坑）

1. **SD 卡不挂载会毁掉整套测量**：设备进手之前跑的是 Matrix Rain（M5GFX/Arduino 系），它会把卡槽 I/O 的
   片上 LDO（chan4）状态改掉，而**该状态跨软复位保留**——之后任何 retro-go（含发行版）都会 `0x107` 超时挂不上卡，
   没有 ROM 就没有游戏。**软件救不回来，只能「彻底断电 + 重插卡 + 上电」**。本次已用干净发行版固件做过对照，
   同样 `0x107`，确认与固件版本无关。
2. **抓日志脚本无时长上限**：`tools/log-tab5-nr.sh <秒数>` 直接循环到时间到，长烤机可以一次抓完。
3. **不要在刷机后立刻解析**：日志尾部会混进下一次刷机的复位与开机行，切窗口要按「第二个 `ESP-ROM`」之前截断。

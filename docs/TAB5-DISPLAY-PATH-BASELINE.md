# Tab5 显示通路 · 基线（P2-1）+ P2-2 A/B 实测

> 目的：在动显示通路之前，先把「每帧平均脏行数」「推屏 fps」两个数字用**真机数据**钉住，
> 后面所有优化都跟这份基线比，不靠感觉。
> 原始数据：`docs/baseline/display-path-A-raw.txt`（A 组，214 窗口 / 213 秒）、`docs/baseline/display-path-B-raw.txt`（B 组，636 窗口 / 635 秒，同时包含稳定性数据）、`docs/baseline/display-path-AA-run1-raw.txt` 与 `display-path-AA-run2-raw.txt`（A/A 噪声底对照，各 213 窗口）。
> 解析脚本：`tools/parse-display-baseline.py`（用 `--first N` 取同一长度的窗口）；多份样本汇总对照用 `tools/parse-aa-noise-floor.py`。

## 一、A 组基线（开关 OFF = 改动前行为）

**采样窗口：213 秒 / 12720 帧（f=1 → 12721）**，ROM = 恶魔城_晓月之圆舞曲，按键时间轴见第三节。

| 指标 | A 组 |
|---|---|
| 推屏帧率 | **60.0 fps**（= 游戏自身节奏，GBA 约 59.7fps） |
| 每帧平均脏行数 | **146.8 行/帧**（整屏 720 行，约 **20.4%** 的行每帧会变） |
| 每帧平均推送次数 | **5.21 次/帧**（`n=` 计数路线），每次平均 **33.08 行** ⇒ 实际推 **≈172 行/帧**、**10341 行/秒** |
| 显示通路占用 | **270.3 ms/s**，即每秒钟约 **27.0%** 的时间花在把画面送上屏 |
| ├ transpose（字节序/旋转） | 122.7 ms/s |
| ├ draw（行拷贝/像素搬运） | 140.0 ms/s |
| ├ overlay / submit | 6.3 / 0.2 ms/s |
| 丢块 | **0 / 66277**（0.0%） |
| 单次推送行数 | 平均 33.08 行，单次最大 84 行 |

参考（同一台设备、**启动器空转**时，另一轮 330 秒采集）：`display=1.75 ms/s`、`blocks=2/秒`、`rows=32 max=32`。
即：**空转时显示通路几乎不花钱，成本全部来自游戏画面的逐帧变化**。

## 二、这两个数字说明了什么

1. **显示通路是第二大开销**：一秒钟里有 0.27 秒在做「把画面送上屏」，其中 transpose（字节序/旋转）与 draw（行搬运）各占约一半。
2. **推送是按"脏行连续段"发的，不是整块 32 行**：一帧平均推 5.21 次、每次约 33.08 行 ⇒ 每帧推 **≈172 行**，
   而"只推真正变化的行"只需 **146.8 行** ⇒ 现在比理论下限**多推 17.4%**
   （多出来的部分是"段与段之间的空隙"：脏行抱团但没抱满一段）。
3. **先算上限，再动手**（避免事后吹）：行级推送最多省 **14.8% 的推送量**；若每行代价不变，壁钟上限约 **3.2% 的每帧时间**。
   也就是说：**不会让 fps 从 60 变成 120**（fps 由游戏节奏决定，本来就不是瓶颈），价值在于省 CPU 时间和减少推送事务数。
4. **帧率目标（≥30fps）本来就满足**：60fps 是游戏节奏，显示通路再差也很少掉下来。
   真正有意义的是稳定性门槛——**用户 2026-10-08 决定豁免原定的「连续 2 小时」**，改为「与 A 同窗短测 + 稳定性信号」。

## 三、A/B 实测（P2-2「只提交变化行」）

同窗（**两边都取前 213 个窗口，帧区间完全一致 f=1 → 12721**）、同 ROM、同按键时间轴；
两份固件**只差一个编译期开关值**，B 组日志里有自证行
`rg_display_dirty_rows_on: display: 只提交变化行 = 开（编译期默认 1，SD 开关 无）`。

| 指标 | A（关） | B（开） | Δ |
|---|---|---|---|
| 推屏 fps | 60.0 | 60.0 | 0% |
| 每帧平均脏行数（内容差异项） | 146.8 | 141.9 | −3.3% |
| **每秒实际推屏行数**（=60×次数/帧×每次行数） | **10341** | **8842** | **−14.5%** |
| 每秒"必须推"的行数（脏行×60） | 8808 | 8514 | −3.3% |
| 相对理论下限的浪费 | +17.4% | **+3.9%** | — |
| 推送次数/帧 | 5.21 | 5.54 | +6.3% |
| 每次推送行数 | 33.08 | 26.60 | −19.6% |
| 每行代价（display 内） | 27.02 µs | 28.01 µs | +3.7% |
| **display 通路占用** | **270.3 ms/s** | **247.7 ms/s** | **−8.4%** |
| ├ transpose | 122.7 | 104.9 | −14.5% |
| ├ draw | 140.0 | 134.8 | −3.7% |
| 丢块 | 0 / 66277 | 0 / 70448 | 0 |
| 复位 / panic / WDT | 0 | 0 | — |

**结论（before → after）**：相对理论下限的**多推量 +17.4% → +3.9%**（A 组三次跑 17.0～17.4%，跨会话稳；本节末尾噪声底小节）；
推屏行数 10341 → 8842 行/秒（−14.5%，信噪比 2.9×，建议读作 **约 −10% ～ −15%**）；
显示通路 270.3 → 247.7 ms/s（−8.4%，信噪比 2.4×），折合每帧时间省 22.6 ms/s ≈ **2.26%**；fps 不变；0 丢块。

**必须一起写出来的保留意见**：

1. **fps 没有提升，也不该有**：60fps 是游戏节奏，显示通路不是瓶颈。真实收益是"每秒省 22.6 ms 的 CPU"。
2. **有内容混淆项**：两次窗口的脏行数差 3.3%（146.8 vs 141.9）——同样的输入时间轴下内容本身略有差别，
   所以 −8.4% 里可能有一小部分来自内容差异，不能全记在技术账上。
3. **收益来自"推得更少"，不是"推得更快"**：每行代价反而**升了 3.7%**（推送次数 +6.3%、每次更碎）。
   相对理论下限的浪费从 +17.4% 降到 +3.9%，这才是它真正的贡献。
4. **事先算的 14.8% 上限被印证**（实测 −14.5% 推送量）；壁钟收益实测 **2.26%**（上限约 3.2%）。
5. **A/A 噪声底已补测（2026-10-08）**，见本节末尾「噪声底」小节；跨会话波动最大 **±5.0%**（行/秒），
   即 −14.5% 的配置效应约为噪声的 **2.9 倍** —— 方向可信，绝对值应读作量级。


### 噪声底（A/A 对照，2026-10-08 补测）

方法：把当年那颗 A 组镜像（`A-baseline-retro-go_v0.4.7-8-g56f98-dirty_tab5.img`）**连刷两遍、各跑同一按键时间轴 300 秒**，
与昨夜那次 A 组数据三方对照（同 ROM、同窗口长度 `--first 213`）：

| 样本 | 脏行/帧 | 次数/帧 | 每次行 | 推屏行/秒 | 相对理论下限 | display ms/s |
|---|---|---|---|---|---|---|
| A（昨夜 00:47） | 146.8 | 5.21 | 33.08 | 10341 | **+17.4%** | 270.3 |
| A/A run1 | 142.0 | 5.02 | 33.09 | 9967 | **+17.0%** | 262.9 |
| A/A run2 | 140.0 | 4.95 | 33.08 | 9825 | **+17.0%** | 260.9 |
| B（开关 ON） | 141.9 | 5.54 | 26.60 | 8842 | **+3.9%** | 247.7 |

- **同会话重复性很好**：run1 vs run2 —— 行/秒 **−1.4%**、display **−0.8%**、脏行/帧 −1.4%，两遍都 0 丢块。
- **跨会话有系统性波动**：昨夜 A 比今晚两遍高 **3.6% / 5.0%**（display 高 2.8% / 3.5%）。
  这是**同一个固件、同一时间轴**下的差异 ⇒ 与 P3-1 的发现同源：**本机 GBA 仿真逐次启动不是位级可复现的**，
  内容因此有几个百分点的漂移。所有 P2-1/P2-2 的绝对值都要按这个量级来读。
- **配置效应**：行/秒 **−14.5%**（对昨夜 A）～ **−11.3%**（对 run1）；display **−8.4%** ～ **−5.5%**。
  以最大跨会话波动为噪声底 ⇒ 信噪比 **2.9×（行/秒）/ 2.4×（display）**。
- **最稳的指标是"相对理论下限的浪费"**：三次 A 全部落在 **+17.0% ～ +17.4%**（跨会话只差 0.4 个百分点），
  而 B 是 **+3.9%** —— 这个比值**对内容漂移几乎免疫**（分子分母同步缩放），是本次改动最可靠的效果量：
  **多推量从约 +17% 降到约 +4%（≈4.4 倍改善）**。

**稳定性（B 组，2026-10-08）**：连续 **635 秒**（帧号 f=1→38101，约 **10.6 分钟**）运行，**0 丢块 / 0 panic / 0 WDT**，
636 个 PERF 窗口无断档；日志中的 `rst:` 行只有两类预期复位（刷机的 `0x17` USB 复位、launcher↔模拟器切换的 `0xc` 软件重启）。
原定的"连续 2 小时"门槛按用户决定豁免（见第二节第 4 条）。

## 四、采集方法（可复现）

```sh
# 1) 固件：诊断构建（临时钩子，验证完必须回退）
#    - RG_GBA_DIAG=1 / RG_GBA_DIAG_SPAM=1  → 每秒打 PERF，每 60 帧打 DIAG_FB
#    - RG_TEST_NO_AUTOSAVE=1               → 禁 SD 自动写，避免污染计时
#    - RG_TEST_MUTE=1                      → 静音（音量写死 0 并落盘；无人值守测试不能吵到人）
#    - RG_TEST_KEYS_DEVICE=<时间轴脚本>     → 无人值守按键（8.0-8.3 按 A；之后每 6 秒换一组方向+A/B）
#    - 启动器侧 rg_test_auto_boot_rom()     → 开机直接进 /sd/roms/gba 下第一个 .gba（免菜单导航）
cd ~/esp32/retro-go-tab5 && . tools/idf-env.sh
cd retro-go-p4 && python3 rg_tool.py --target tab5 --no-networking build-img launcher gbsp
cd .. && sh tools/flash-tab5.sh retro-go-p4/retro-go_<ver>_tab5.img 330 > /tmp/p21-A.log 2>&1

# 2) 解析：两边必须取同一窗口长度（--first N），否则窗口不同、结论不可比
python3 tools/parse-display-baseline.py /tmp/p21-A.log --first 213
python3 tools/parse-display-baseline.py /tmp/p22-B.log --first 213

# 3) A/A 噪声底（同一颗 A 镜像连跑两遍，各 300 秒，再与前一次 A 对照）
sh tools/flash-tab5.sh ~/.hermes/cache/scratch/A-baseline-*.img 300 > /tmp/AA-run1.log 2>&1
sh tools/flash-tab5.sh ~/.hermes/cache/scratch/A-baseline-*.img 300 > /tmp/AA-run2.log 2>&1
python3 tools/parse-display-baseline.py /tmp/AA-run1.log --first 213
python3 tools/parse-display-baseline.py /tmp/AA-run2.log --first 213
```

- **A/B 可比性**：两次构建只差「变化行开关」一个值；ROM、按键时间轴、窗口长度完全相同（帧区间一致）。
- **按键时间轴**：`8.0-8.3:A` 之后每 6 秒一组（`RIGHT|A`,`LEFT|A`,`DOWN|A`,`UP|A`,`RIGHT|B`,`LEFT|B`,`DOWN|A`,`UP|B`），
  A 组覆盖到 302 秒，B 组延长到 1800 秒（**前 300 秒与 A 逐字相同**）。

## 五、现场注意事项（踩过的坑）

1. **SD 卡不挂载会毁掉整套测量**：设备进手之前跑的是 Matrix Rain（M5GFX/Arduino 系），它会把卡槽 I/O 的
   片上 LDO（chan4）状态改掉，而**该状态跨软复位保留**——之后任何 retro-go（含发行版）都会 `0x107` 超时挂不上卡，
   没有 ROM 就没有游戏。**软件救不回来，只能「彻底断电 + 重插卡 + 上电」**。本次已用干净发行版固件做过对照，
   同样 `0x107`，确认与固件版本无关。
2. **抓日志脚本要容忍端口重枚举**：刷机后 USB 会重新枚举，端口会短暂消失/改名；旧版开场直接 open 会
   `OSError: [Errno 6] Device not configured` 立刻退出（真机实测：整轮 0 行日志）。`tools/log-tab5-nr.sh` 已修。
3. **不要在刷机后立刻解析**：日志尾部会混进下一次刷机的复位与开机行，切窗口要按「第二个 `ESP-ROM`」之前截断。
4. **A/B 必须同窗**：否则两边窗口长度不同（实测踩过 199 秒 vs 202 秒），数字不可比。用 `--first N` 固定。

# 横竖屏切换评估（Tab5）· 讨论记录 2026-10-08

> 用户已定方向（2026-10-08）：**两种方向都用 720×480 的游戏画布（GBA 3x）**，横屏的留白当按键，
> **暂时不做全屏**；切换方式 = **开机选 + 重启生效（方案 B）**。
> 本文按这个设计重写；旧评估里"横屏像素 2.67×"的担忧**作废**（见 §三）。

## 一、已确认的设计

| | 竖屏（现状，0.4.x） | 横屏（老线，M5Burner 0.2/0.3） |
|---|---|---|
| 逻辑画布 | 720×1280（游戏带 720×480） | 1280×720（整屏 UI） |
| 游戏画布 | **720×480**，锚定顶部 y[0,480) | **720×480**，居中 x[280,1000) y[120,600) |
| 按键 | 下方 y[480,1280)（800px 高） | 四周留白：左/右各 280、上/下各 120 |
| 启动器 | 画在 720×480 带内，按键在带外 | 画满 1280×720，按键**浮在菜单上** |
| 触摸表 | `touch_layout.h`（十字 84×84 @(170,780)、动作键 @(550,780)…） | 同文件另一份（十字 92×92 左列 @(140,420)、动作键右侧…） |

**两边的游戏画布完全相同 = 345,600 px。** 缩放算法、核心层、滤镜、存档、封面全都不受方向影响。

## 二、这套横屏形态不是要新设计，是已经跑过的

`exp/display` 线上的 M5Burner **0.2 / 0.3 就是横屏发布**（`c630137 release: M5Burner 包 v0.3`），
0.4~0.4.8 才是竖屏线。⇒ 横屏长什么样不用凭空设计，可以直接拿 0.2/0.3 的实机效果当视觉参照
（差别只在：那时靠 frameskip 撑帧，现在的管线不该重开那些历史包袱）。

## 三、作废：我先前说的"横屏要写 2.67 倍像素"

那条基于"横屏 = 游戏拉满 1280×720"的假设。按你定的设计（横屏游戏窗也只有 720×480），
**两种方向每帧要推的像素量一模一样**，横屏唯一多出来的是**访问模式**：逻辑画布 1280×720 映到物理
720×1280 需要 90° 旋转（横屏驱动就是这么做的：E3 分块 + 片内 SRAM 转置），竖屏则是线性顺序写。

## 四、唯一的新取舍（需要你拍板）：横屏 GB/GBC 掉一档

`rg_display.c` 的 ZOOM 规则：`max_zoom = min(可用宽/源宽, 可用高/源高)`。
两种方向的"可用宽"都是 720（竖屏 = 屏宽；横屏 = 1280 − 两侧各 280 ×2），差的只有"可用高"：

| 机种 | 竖屏（可用高 620 = 1280−660） | 横屏（可用高 480 = 720−上下各 120） |
|---|---|---|
| GBA 240×160 | 3× → 720×480 | 3× → 720×480（**相同**） |
| NES 256×240 | 2× → 512×480 | 2× → 512×480（相同） |
| SNES 256×224 | 2× → 512×448 | 2× → 512×448（相同） |
| GW 96×64 | 7× → 672×448 | 7× → 672×448（相同） |
| **GB/GBC 160×144** | **4× → 640×576** | **3× → 480×432（小一档）** |

横屏要把 GB/GBC 也做到 4×，唯一的办法是**重排按键、把上下留白从 120 压到 ~60**（可用高 600），
代价是肩键/功能键得挤进两侧 280px 里 —— 拿"两侧手感"换"GB 大一档"。
**我的建议：先用现状（横屏 GB 3×），把"腾高度"留作后续可选项。**

## 五、成本重心：不是性能，是"两份合一份"和两套 UI

- **不是性能**：游戏画布相同、物理面板相同 ⇒ 横屏不增加像素量；性能上只剩"旋转访存"这一个变量，
  而横屏驱动里那套（E3 分块转置 + AXI-ICM 提权）**已经实现并在 0.2/0.3 上真机跑过**
  （旧数字：整屏推送时显示 431ms/s、靠 frameskip；但那是"推整个 1280×720"，
  你的设计只推 720×480 游戏带 + 按键变化时推按键 ⇒ 写量降到约 1/4，**必须实测**：不预告倍数）。
- **是合代码**：竖屏驱动 `mipi_dsi_tab5_p.h` 与横屏驱动 `mipi_dsi_tab5.h` 是**同符号的两份拷贝**
  （`TAB5_PHYS_W/H`、`tab5_fb`、`lcd_*`…，各约 975 行、约 90% 相同），不能同时 include
  ⇒ 要合成一份、把映射（线性 vs 90°）做成分支。
- **是几何收敛**：几何目前是编译期宏，共享层有 4 处直接吃它
  （`rg_display.c` 的 `LCD_BUFFER_LENGTH` / 两个 map 数组 / `screen_line_checksum[]` / `.screen.*`；
  `rg_touch_skin.c` 的面板 surface；`rg_touch_overlay.c` 的界带；`config.h` 的默认边距）
  ⇒ 收敛成一张"方向表"，数组按 max（1280×1280）分配，内存增量约 10KB。
  **好消息：三个 app（launcher/gbsp/retro-core）直接引用几何 = 0 处**，它们只从 `display.screen.*` 拿尺寸。
- **是 UI 视觉**：启动器在两套画布下的布局（竖屏 720×480 带内 / 横屏满 1280×720 + 按键浮层）
  两份都已存在，但**各看一遍真机**是必须的工作量（不是技术风险，是审美确认）。

## 六、落地路径（三步，每步可单独验收）

### S1 · 编译期开关（先做这个）
`RG_TAB5_ORIENTATION`（默认竖屏 = 现状零变化），把方向相关的量收进一张表：
几何 / 映射 / 视口上限 / 默认与最大缩放 / 字体倍数 / `LCD_BUFFER_LENGTH` / 触摸表指针；
两份驱动合并成一份（映射先走编译期分支）。
**产出两个镜像**，同时完成两件事：① 量横屏在**当前管线**下的 PERF（`xpose/ovl/draw`、BUSY、skipped）；
② 横屏 UI 真机过一遍眼。
—— 这一步同时就是 S2 的前置重构（几何从宏变成表），不白做。

### S2 · 开机选择 + 重启切换
① NVS 存 `orientation`（沿用 `NS_GLOBAL` 先例）；② 首次开机（键不存在）弹一页选择（两个方向预览图 + 触摸点选）；
③ 设置菜单加「屏幕方向」，改后写 NVS + 提示"重启生效"；④ 启动早期（`rg_display` init 之前）读 NVS 选表。
验收：来回切两次、掉电保留、两方向各跑一局（含 GB/GBC 与 SNES 的读档）。

### S3 · 可选清理
`ppa_engine` 被 `COMPONENT_REQUIRES` 链进构建图但**全树无调用者**（PPA 已定案 CPU 直写）⇒ 可从构建图摘掉。

**不做**：热切换（C，运行中换方向）—— 显示任务重入/面板重配/触摸层重建/整屏重画，且文档里有前科
（E2 `num_fbs`、只改分辨率 → 必失败）。

## 七、PPA（回答"如果有收益我还是想试试"）

- 已量三形态（§125）：整帧 16.8ms/帧 vs CPU ~7.5ms；按块 ×15 = 1129µs vs 566µs ⇒ 定案 CPU 直写。
- **横屏场景下更没戏**：整帧旋转要搬 1.84MB 进 + 1.84MB 出 = 3.7MB，@82MB/s ≈ **45ms/帧**。
- 唯一**没量过**的变体是**非阻塞**（`NON_BLOCKING` + `done_cb` + 双缓冲），理论上能去掉"白等硬件搬完"。
  但推演上仍赢不了：CPU 路径瓶颈是"从 PSRAM 读源"一趟（~92MB/s 上限），写靠 cache 合并、不必立刻落 PSRAM；
  PPA 是纯 DMA，**读和写两趟都真实占带宽** ⇒ 零等待时带宽占用也是 CPU 路径的约 2 倍。
  **这是推演、不是实测。** 要关掉这个洞：现有探针 `mipi_dsi_tab5_p.h: TAB5_PPA_PROD_PROBE` 加一个非阻塞变体，
  成本 = 一次构建 + 一次刷机。

## 八、需要拍板的点

1. **横屏 GB/GBC**：接受 3×（现状设计），还是为它重排按键把上下留白压到 60 换 4×？
2. **首次开机**：要不要做"方向选择页"（我建议做，一次性、体验清楚），默认值取竖屏？
3. **横屏 UI**：S1 就一次把横屏启动器/菜单视觉定稿，还是先保证可用、视觉后续单独一轮？
4. **PPA 收尾**：那个没量过的非阻塞变体（一次构建 + 一次刷机），要不要顺手关掉这个洞？

### 真机首刷 + 第一轮反馈（2026-10-08 深夜）

首刷横屏镜像后，启动日志给了三条**方向生效的铁证**（不是推断）：
```
lcd_init: Tab5 DSI ready (ST7123 path): logical 1280x720 -> physical 720x1280 (90CW map)
update_viewport_scaling: zoom source 240x160 requested x3 → x3 (720x480), max x3, ctrl left 240
rg_dpad_geom_update: dpad: 中心 140,420 / 臂距 85 / 可触 170 / 死区 30 / 斜向门槛 70
（→ 240x160@1.500 => 720x480@1.500 left:280 top:120）
```
第三条尤其中要：十字键的矢量判定几何是**从键位表算**出来的，所以横屏不用改 `rg_input.c` 就成立。

同时暴露两个"横屏从没被真机验证过"的问题：
1. **皮肤面板照样装了**（`touch skin: viewport changed (x=0 w=720 top=480) → (x=280 w=720 top=600), re-installing panel`），
   而面板里铭牌的 x 是**写死的 360（竖屏半宽）**、y 由"控制区"推导 → 真机上铭牌落在游戏画面左下角那块。
2. 启动 30s 日志里有 **54 条 `previous draw operation is not finished`**（面板 DMA 排不上）。
   横屏不能用竖屏那套"32 行/块"（1280×32×2B = 80KB 撑爆 48KB 片内暂存），只能 16 行/块 → 推送更碎。
